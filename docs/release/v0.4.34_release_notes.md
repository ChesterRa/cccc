# CCCC v0.4.34-rc4 Release Notes

This release candidate validates the complete pip distribution with its bundled
Rust implementation, plus an optional experimental standalone Rust preview,
before the stable `v0.4.34` release.

`v0.4.34-rc4` brings the native Rust implementation onto the same product and release
line as CCCC's Python distribution, adds Cline as a first-class runtime, and
tightens the authorization and release boundaries that matter when CCCC is used
across multiple Working Groups.

## RC4 Stabilization Since RC3

RC4 concentrates the changes made after RC3 into one release-tested candidate.
Voice Secretary now keeps the Group and document captured at recording start even
when the operator navigates elsewhere, bounds native ASR memory at silent
endpoints, and lets long recordings finish promptly while speaker analysis waits
for the active inference lease. Final ASR timeout invariants remain runtime-checked
under Clippy's warnings-as-errors policy.

Delivery preferences and actor lifecycle projections now stay aligned across
recovery paths. The combined CLI follows embedded-daemon loss through an
event-driven signal, capability discovery emits the autoload candidate expected
by clients, and the Web capability picker includes its complete localized labels.
Python and Rust startup banners now advertise a LAN URL only when the Web listener
is actually bound to a wildcard address; the default loopback listener reports
only its local URL.

Native capability installation now commits enablement and slash visibility
atomically, publishes one durable change event for a semantic catalog update, and
keeps Web slash commands current across request races, SSE reconnects, and polling
fallback. Claude headless recovery also invalidates a resumed session when its
provider exits after the startup grace period without allowing a later metadata
write to restore that stale session.

The release gates themselves are less sensitive to runner contention. Combined
daemon/Web lifecycle tests run in an isolated serial job, native distribution and
Windows installer checks run after merge, and stable aggregate checks summarize
both stages. Dependabot continues updating normal GitHub Actions while leaving
the intentionally pinned Rust 1.88 toolchain ref under manual version control.

## One CCCC Installation, Two Implementations

Python uses PEP 440 `0.4.34rc4`, Rust uses SemVer `0.4.34-rc4`, and both map to
the canonical `v0.4.34-rc4` tag. The release candidate is published to TestPyPI.
The stable and recommended `cccc-pair` distribution keeps Python as its initial
default and bundles a private Rust executable in supported platform wheels.
Other pip platforms retain the universal Python fallback. Linux x86-64, Intel
and Apple Silicon macOS, and Windows x86-64 users may also evaluate an
experimental standalone Rust preview from GitHub Pages without installing Rust
or Python; that preview has no Python fallback or implementation switching.

Both implementations use the same `CCCC_HOME`, group documents, append-only
ledgers, actor contracts, daemon IPC model, MCP surface, and Web frontend. Native
wheel candidates are dependency-repaired, installed, and switched in both
directions on every supported target. Standalone binaries execute on each native
build host, and final installer candidates are exercised on Linux and Windows. A
dedicated interop gate covers the shared persisted-state contracts. The complete
source, universal, and native artifact set is then published once to the
appropriate Python package index (TestPyPI for this RC), and tags no longer
publish a parallel crates.io product.

`cccc rust [command ...]` and `cccc python [command ...]` persist the selected
implementation and optionally run a command. `cccc status` reports the selected,
running, and available implementations. The launcher validates exact payload
version parity before a switch, explicitly replaces the active Web/daemon pair,
and never silently falls back. In the experimental standalone preview,
`cccc update` uses the website installer; in the recommended pip installation it
updates both implementations as one product.

## Cline Joins the Runtime Catalog

Cline is now covered as a formal PTY runtime rather than a custom command. CCCC
can discover the installed CLI, create actors with the supported TUI defaults,
install or repair the `cccc mcp` stdio server through Cline's own MCP command, and
show the runtime consistently in the CLI, diagnostics, Web actor editor, profiles,
and runtime documentation.

The integration uses Cline's configuration boundary instead of editing unrelated
Node or npm state. Re-running setup repairs the single named `cccc` server entry,
which keeps installation deterministic when the CCCC executable path changes.

## Safer Multi-Group Web Access

The supported `?token=` URL remains available for bootstrapping a browser session.
Its transport does not change what the token may access: a Group-scoped token sees
global notifications only for its assigned Groups.

The global SSE channel now contains routing metadata only. Message bodies and
other complete event fields stay on the authorized per-Group stream. Capability
blocking is also treated as an administrative operation, closing a route that
previously accepted scoped credentials.

## More Predictable Recovery and Delivery

The Rust backend closes a broad set of compatibility gaps around actor recovery,
inbox cursor migration, Group Bridge route health and revocation, tracked sends,
headless delivery, daemon shutdown, and Web terminal replay. The Web UI also keeps
chat and terminal anchors stable across view changes and reconnects, reducing the
number of situations where recovered state looked stopped, incomplete, or
read-only. On iOS, the app now follows both the height and top offset of the
visual viewport, keeping the composer above the keyboard when WebKit pans the
page during focus.

Terminal reconnect handshakes now take both replay cursors from the exact PTY
backlog snapshot being attached. Output produced during the handoff is therefore
classified as live output instead of being mistaken for replayed history.
Rust terminals now use the `term_attach` raw stream end to end instead of polling
the daemon every 50 ms and converting output through JSON. The runtime publishes
cursor changes from its bounded PTY history, the daemon pumps raw output and input
concurrently, and Web forwards 64 KiB chunks while pacing delivery against xterm's
parsed-output cursor with a 256 KiB in-flight window. Control/viewer ownership,
explicit takeover, reconnect cursors, non-UTF-8 bytes, and legacy WebSocket clients
remain supported; keyboard input stays responsive while replay is backpressured.
Writer-status polling no longer takes a Group write lock, and later resize requests
carry the attachment identity so a replaced controller cannot resize the shared PTY.

New Web terminals now negotiate a Rust-maintained ANSI screen snapshot at the
exact raw-output cursor and open directly on the latest PTY state. Live traffic
after that fence remains byte-for-byte raw, valid reconnect cursors remain
tail-only, and expired cursors receive a fresh snapshot. Split UTF-8/escape
sequences and Kitty keyboard modes survive the handoff; unsupported graphics,
unsafe dimensions, or oversized snapshots fail safely back to the existing raw
replay protocol. The browser parses snapshots at their encoded grid before
refitting the visible xterm, and terminal clear now resets the mirror as well as
raw history so cleared scrollback cannot reappear on a fresh attach.

Rust Web now resolves latest Voice Secretary sessions and transcript clearing
through the active daemon. Persistent document transcripts remain visible after
bounded state pruning, while a clear uses the daemon's cross-engine lock and
removes both session and document logs. Speaker-diarization completion also returns
through the daemon's canonical session updater, preserving normalized fields and
the 50-session projection bound. Legacy Python `window_segments` and
mixed-document segment filtering remain compatible with the Rust session view.

Codex PTY recovery now persists the fenced `SessionStart.session_id` reported by
the current launch instead of depending on the human-readable `/status` layout.
The next compatible actor start can therefore issue `codex resume <session_id>`
even when newer Codex versions omit the session field from `/status`; the old
parser remains available as a delayed compatibility fallback.

Remote Group Bridge pairing no longer assumes every public endpoint responds
within three seconds. Rust now separates a five-second connection budget from a
15-second total request budget, Python uses the same 15-second pairing budget,
and both implementations preserve actionable timeout, DNS, TLS, proxy, and
connection diagnostics without automatically retrying a non-idempotent POST.

Python inbox cursors now use the ledger's append order as their authority too.
Two events with the same timestamp—or a clock adjustment that makes a later event
look older—can no longer cause unread work to be skipped.

The Rust MCP now routes the core `cccc_inbox_mark_read` tool directly to the
daemon's single-event or filtered mark-all operation according to its `action`.
Core inbox acknowledgements therefore advance the authoritative read cursor
instead of being misclassified as optional capability tool calls.

## Upgrade Notes

- No ledger or Group data migration is required. In the pip distribution, use
  `cccc rust` or `cccc python` to switch; the launcher owns stopping the active
  process pair and prevents two implementations from writing the same
  `CCCC_HOME` concurrently. The standalone preview contains Rust only.
- Existing Access Tokens continue to work. Group-scoped tokens now receive less
  data from the global stream, as intended; per-Group views continue to receive
  complete authorized events.
- Existing custom Cline actor commands remain valid. New actors use CCCC's formal
  Cline defaults, and `cccc setup --runtime cline` can repair the MCP entry.
- Manual release dispatches perform build and verification only. A pushed
  `v0.4.34-rc4` tag publishes the Python artifacts to TestPyPI; the experimental
  standalone archives, checksums, and installers are published only when an
  operator separately runs their workflow on that matching tag.

## Why Upgrade

Test this release candidate through TestPyPI when you want to validate the bundled
Rust implementation, use Cline alongside other agents, operate Group-scoped Web
access, or exercise the Rust backend's delivery and recovery parity. The product
model remains unchanged: one recommended pip distribution, one CCCC contract,
one version identity, and two implementation choices inside supported wheels.
